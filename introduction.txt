règle importante

les calculs métier restent dans ms-python-2

MCP ne refait pas les calculs

tool.py récupère les données en appelant FastAPI

gemma 4 ne doit pas inventer les données energIA

la réponse doit être construite à partir du JSON retourné par FastAPI


-----------------
services docker
-----------------

gateway

ce service utilise node js et express
il écoute sur le port 3000
il fournit l’interface web
il transmet les requêtes aux services python et au serveur MCP


ms-python

ce service utilise FastAPI
il écoute sur le port 8000
il contient le premier moteur historique du projet


ms-python-2
ce service utilise FastAPI
il écoute sur le port 8002
il contient le moteur temporel actuel avec les phases 1 2 et 3


llm
ce service utilise ollama
il écoute sur le port 11434
le modèle utilisé est gemma4:e4b

mcp-server
ce service utilise FastMCP
il écoute sur le port 8003
il expose les ressources les outils MCP et la route HTTP de l’assistant

---------------------------
mcp_server
---------------------------

mcp_server/dockerfile
ce fichier construit l’image du serveur MCP
il installe les dépendances de requirements.txt
il copie les fichiers python
il démarre server.py sur le port 8003

mcp_server/requirements.txt
ce fichier contient les dépendances python
mcp fournit le protocole Model Context Protocol
httpx permet d’appeler FastAPI
ollama permet de communiquer avec gemma 4
python-dotenv permet de charger le fichier env

mcp_server/tool.py
ce ficier est le client HTTP de FastAPI
PROJECT_ROOT retrouve le dossier racine du projet
ENV_FILE indique le chemin du fichier env
load_dotenv charge la configuration pendant une exécution locale
_get_api_data construit une requête HTTP vers FastAPI
_get_api_data ajoute SECURITY_TOKEN dans l’en-tête x-api-key
_get_api_data gère les délais les erreurs HTTP les erreurs réseau et le JSON invalide
get_plants appelle GET /phase1/plants
get_plants vérifie le nombre et la liste des centrales
get_region_consumption appelle GET /phase1/consumption
get_region_consumption sélectionne une région et un horaire
get_region_consumption retourne region_id timestamp et consumption_mw
get_phase3_simulation appelle GET /phase3/simulate-day
get_phase3_simulation transmet le scénario le nombre de pas et la réserve minimale
get_phase3_simulation retourne le résultat sans refaire les calculs


mcp_server/server.py
ce fichier crée le serveur MCP
_to_json transforme une donnée python en texte JSON
list_plants est un outil MCP qui retourne les centrales
get_consumption est un outil MCP qui retourne la consommation d’une région
simulate_phase3 est un outil MCP qui lance une simulation phase 3

plants_resource expose energia://plants
consumption_resource expose energia://consumption/{region_id}/{timestamp}
phase3_resource expose energia://phase3/{scenario_id}/{number_of_steps}/{minimum_reserve_mw}
POST /assistant reçoit une question depuis la gateway
POST /assistant contrôle x-api-key
POST /assistant appelle ask_energia
GET /health vérifie le serveur MCP


mcp_server/ollama_client.py
ce fichier crée la connexion avec ollama
OLLAMA_HOST contient l’adresse du service ollama
OLLAMA_MODEL contient gemma4:e4b
ask_ollama vérifie le prompt
ask_ollama envoie le prompt à gemma 4
ask_ollama récupère la réponse
ask_ollama refuse une réponse vide
main permet de tester ollama depuis le terminal


mcp_server/orchestrator.py
ce fichier coordonne MCP FastAPI et ollama
parse_question accepte actuellement le format consommation région heure

exemple

consommation occitanie 18:00
parse_question retourne region_id et timestamp
read_consumption construit l’adresse de la ressource MCP
read_consumption se connecte au serveur MCP
read_consumption lit la consommation
read_consumption transforme le résultat JSON en dictionnaire python
build_prompt ajoute la question et les données energIA dans le prompt
ask_energia exécute le parcours complet
ask_energia retourne la question les étapes les données et la réponse
main permet de poser une question depuis le terminal
limite actuelle
gemma 4 ne sélectionne pas encore automatiquement un outil MCP
python sélectionne la ressource de consommation
gemma 4 utilise ensuite la donnée pour rédiger la réponse

services/graph_loader.py

charge les consommations les productions renouvelables et les scénarios
services/nuclear_dataframe.py
fusionne les données générales et temporelles des centrales dans une DataFrame
services/dijkstra.py
recherche le chemin le plus court entre deux centrales
services/capacity.py
calcule la marge disponible

services/priority.py

services/candidates.py
sélectionne les centrales disponibles pour une région


services/score.py
calcule le score utilisé pour classer les centrales

services/allocation.py
répartit une demande entre les centrales candidates

services/temporal_allocation.py
répartit les variations entre les régions
conserve l’état des centrales entre les allocations

services/temporal_engine.py
construit l’état initial des centrales
calcule un quart d’heure
enchaîne les 96 pas
calcule la réserve le surplus et les MW manquants


services/apply_consumption_events.py
détermine si un événement est actif
calcule la variation de l’événement

services/scenario_json.py

services/charts.py
génère les graphiques de la phase 2

services/long_simulation.py
répète les données journalières

services/energia_service.py
contient une façade métier expérimentale

services/dispatch.py

--------------------
limitations actuelles
-----------------

la question doit encore respecter le format consommation région heure
exemple consommation occitanie 18:00

la consommation retournée est une consommation de référence
elle ne représente pas une mesure en temps réel
gemma 4 ne choisit pas encore automatiquement l’outil MCP
une simulation phase 3 complète peut produire un très grand JSON
les réponses de gemma 4 peuvent varier
mcp_server ne possède pas encore de tests automatisés
